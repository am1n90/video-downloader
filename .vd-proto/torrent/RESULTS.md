### 5. Находки, важные для Этапа 1

1. **`alert.message()` может бросить `UnicodeDecodeError`** на русской Windows:
   libtorrent обрезает системный текст ошибки посреди многобайтовой буквы.
   Любой вызов `message()` в приложении — через защитную обёртку.
2. **Занятый файл → раздача молча в `upload_mode`**: `file_error_alert`, но
   `errc` пустой, состояние «downloading», пиров 0. `clear_error()` + `resume()`
   не помогают; libtorrent сам повторит только через `optimistic_disk_retry`
   = 600 с. `unset_flags(upload_mode)` после освобождения — загрузка через 2.0 с.
   Движку: ловить `file_error_alert` → понятная ошибка + «Повторить».
3. **Закрытие сессии до 5 с** — `closeEvent` должен закрывать сессию с
   ограничением по времени и не блокировать выход дольше.
4. **`.parts`-файл** при частичном выборе файлов — удалять вместе с раздачей.
5. `dht_state.nodes` в обёртке не читается (нет конвертера) — сохранять
   DHT-состояние только буфером `write_session_params_buf`.
6. `torrent_info.trackers()` помечен deprecated — в коде использовать новый API.

### 7. HTTP Range-сервер (stdlib ThreadingHTTPServer), probe_http.py

**Первая версия отдавала нули.** 8 PASS / 3 FAIL — во всех проверках, где
сервер ждал недокачанные куски, байты не совпали с источником. Диагностика
(4 диапазона): расхождения — 100% нулевые байты, начинаются ровно на
границе куска (0) или блока (256 КБ), на диске через мгновение уже
правильные данные. Причина: `have_piece()` = true сразу после проверки хэша,
а запись ещё в очереди дискового потока libtorrent 2.x; sparse-файл в этот
момент читается нулями, а не коротким чтением.

**Исправление:** данные только через `h.read_piece()` → `read_piece_alert`
(кэш кусков 64 МБ). Диагностика 4/4 совпадают; probe_http — **11 PASS / 0 FAIL**:

| Проверка | Итог |
|---|---|
| HEAD: 200, Content-Length, Accept-Ranges, video/x-matroska | OK, 2 мс |
| Range 0-99 / суффикс -1000 / 416 за концом файла | OK |
| Range 2 МБ на 60% (куска не было) | OK, 2.0 с |
| Обрыв клиента посреди ответа → следующий запрос | OK |
| Чужой токен → 404, чужой Host → 403 | OK |
| 4 параллельных диапазона по 4 МБ | OK, 5–6 с |
| keep-alive: 2 запроса в одном соединении | OK |
| Слушает только 127.0.0.1 (netstat) | OK |

VLC сбрасывает keep-alive соединение при перемотке → `ConnectionResetError`
[WinError 10054] в `handle_one_request` → socketserver печатает traceback.
Безвредно; в прототипе перехвачено в `Handler.handle()`.

### 14. Вариант A: скорость с входящими соединениями выключенными на уровне клиента

По решению владельца 16.09.2026 — вместо создания новых правил Windows
Firewall (что потребовало бы прав администратора для последующего
удаления), сравнение выполнено настройкой самого libtorrent:
`enable_incoming_tcp`/`enable_incoming_utp` = false. Функционально это
даёт тот же эффект, что блокировка брандмауэром (клиент не принимает
входящие), без системных изменений и без прав администратора. Честное
парное сравнение: тот же процесс, та же раздача (Sintel), то же время
суток — переключается только одна настройка между прогонами.

**Находка по дороге (важно для точности всех похожих замеров):** первая
попытка использовала общую папку сохранения без очистки между прогонами —
клиент находил уже полностью скачанный файл с прошлого прогона и просто
досиживал (0.0 МБ/с — не сеть, а состояние диска). Исправлено: каждый
прогон — своя папка, удаляется после.

| Прогон | Входящие | Метаданные | Скорость (сред./пик) | Пиры (макс.) | Входящих (макс./сред.) |
|---|---|---|---|---|---|
| 1 | вкл | 1.62 с | 2.15 / 6.76 МБ/с | 188 | 0 / 0 |
| 2 | выкл | 1.72 с | 2.24 / 9.09 МБ/с | 188 | 0 / 0 |
| 3 | вкл | 1.71 с | 2.25 / 8.14 МБ/с | 190 | 1 / 0.2 |
| 4 | выкл | 1.82 с | 2.12 / 8.28 МБ/с | 189 | 0 / 0 |

**ИСПРАВЛЕНИЕ 16.09.2026 (см. §16): колонка «Скорость (сред.)» — не
скорость скачивания.** Это среднее за фиксированное окно 60 с, а файл
Sintel (123 МБ) докачивается за 24–30 с; остальные ~30 с скорость 0 и
пиров 0 (раздача завершена). Реальная скорость во время скачивания —
медиана 4.7–5.3 МБ/с, пик 8–9 МБ/с. Одинаковые «2.2 МБ/с» во всех
прогонах — это просто 128 МБ / 60 с.

Вывод про входящие остаётся осторожным: заметной разницы нет (все прогоны
докачали файл в пределах окна, пики 6.8–9.1 МБ/с в обоих режимах), но
метрика была выбрана плохо — для честного сравнения нужно время до 100%
или скорость на большом файле. Реально входящих при «вкл» — 0-1. Открытый
вопрос — важны ли входящие для стриминга (Этап 2) — не проверялось.

### 15. Запуск exe без прав администратора

Отдельной учётной записи обычного пользователя нет — использован тот же
пользователь с отфильтрованным токеном: `runas /trustlevel:0x20000`
(не требует прав администратора и пароля — фильтрует ТЕКУЩИЙ токен: снимает
возможность использовать группу Administrators, не создаёт нового
пользователя). Подтверждено `whoami /groups` под этим токеном:
`BUILTIN\Администраторы` присутствует, но помечена **«группа, используемая
только для запрета» (Deny Only)** — процесс физически не может
воспользоваться правами администратора. Уровень целостности — Medium
(S-1-16-8192).

`pack_probe.exe` под этим токеном: **PACK_OK, exit code 0**, создание
раздачи и переход в seeding за 0.14 с — как и под полным токеном.

**Оговорка:** это приближение к «обычному пользователю», не то же самое,
что отдельная учётная запись Windows с профилем `%LOCALAPPDATA%` другого
пользователя — не проверялось.

### 16. Почему «2.2 МБ/с при 30 пирах» — расследование (16.09.2026)

Вопрос владельца: интернет 1 Гбит/с (~119 МБ/с), 30 пиров, а скорость 2.2 МБ/с.
Диагностика: снимок каждые 2 с — подключённые пиры, сколько из них реально
шлют данные (payload > 1 КБ/с), распределение скорости по пирам, доля трёх
самых быстрых; Sintel и Ubuntu 26.04.1 (6.2 ГБ), настройки по умолчанию и

**Ответ:**
1. **«2.2 МБ/с» — ошибка метрики, не скорость.** Среднее за 60 с по файлу,
   который докачивается за 24–30 с. «30 пиров» в логах — момент старта
   (1.6 с после запуска); дальше подключалось до ~190.
2. **На Sintel ограничение — сами пиры.** Из ~34 подключённых данные шлют
   ~23; основная масса отдаёт 100–500 КБ/с (11–15 пиров), быстрее 1 МБ/с —
   0–1 пир, 5–15 пиров шлют < 50 КБ/с. Сумма — 5–9 МБ/с. Это маленькая
   демо-раздача WebTorrent со слабыми сидами.
3. **На Ubuntu тот же код и те же настройки — 40.6 МБ/с в среднем и 68.8 в
   пике** (80–90 пиров шлют данные, 13–16 из них быстрее 1 МБ/с), скорость
   ещё росла к концу окна. Код и настройки скорость не режут.
4. **«Разгон» настроек не помог:** Sintel 5.3 против 4.7 МБ/с (в пределах
   разброса), Ubuntu хуже — 35.9 против 40.6 (разброс роя; больше
   соединений, но доля быстрых пиров меньше). Менять настройки по умолчанию
   для скорости нет оснований.
5. Потолок 1 Гбит/с на этой машине не достигнут: пик 68.8 МБ/с ≈ 58%
   канала за первую минуту, с разгоном TCP и запросов. Где потолок при
   длительном скачивании (диск, CPU, Wi-Fi 5G) — не проверялось.

Попутная поправка к собственной диагностике: флаг `peer_info.choked` —
это «МЫ заглушили пира» (наша отдача), а не «пир заглушил нас»; поле
«unchoked_us» в скрипте фактически считало наши слоты отдачи (8 = 
unchoke_slots_limit), а не разрешённых нам пиров. Выводы опираются на
payload_down_speed каждого пира — эта метрика верная.
